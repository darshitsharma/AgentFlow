1. Executive Summary

AgentFlow is a full-stack AI agent orchestration platform that allows users to create, configure, and connect AI agents into collaborative workflows. Each agent runs on a real LangGraph runtime powered by a local Ollama LLM (llama3.1:8b), executes real tools (web search, code execution, calculator, weather, etc.), and maintains semantic memory across conversations.

Agents can be connected into visual multi-agent workflows using a drag-and-drop React Flow builder with support for sequential pipelines, fan-out/fan-in patterns, conditional routing, and feedback loops. The platform integrates with Telegram as an external messaging channel, enabling end-users to interact with individual agents or entire workflows conversationally.

Key capabilities at a glance:

  • 15+ configurable dimensions per agent (name, role, system prompt, model, tools, channels, schedule, memory, skills, guardrails, interaction rules, max tokens, temperature, active status)
  • 8 executable tools — web search, calculator, code executor, file reader, weather, summarizer, datetime, remember-fact
  • Two-tier semantic memory — short-term (per-conversation) + long-term (persistent facts) using ChromaDB + sentence-transformers
  • Visual workflow builder with fan-in merging, conditional edges, feedback loops, and 2 pre-built templates
  • Telegram integration supporting both single-agent and full-workflow routing with background processing and deduplication
  • Live monitoring dashboard with real-time logs, inter-agent messages, and token tracking
  • 16 automated tests covering agent CRUD, workflow execution, and message delivery

Criterion LangGraph CrewAI AutoGen
Graph-based control flow ✅ Native StateGraph ❌ Sequential only ❌ Chat-based
Custom tool integration ✅ LangChain @tool ⚠️ Limited ⚠️ Complex setup
State management ✅ TypedDict state ❌ Implicit ❌ Implicit
Ollama compatibility ✅ First-class ⚠️ Partial ⚠️ Requires wrappers

Decision: LangGraph gives us explicit control over the agent execution graph — each node is a function, edges carry state, and we can insert tool nodes, memory nodes, and condition checks at precise points. This maps perfectly to our workflow engine's BFS execution model.

6. Agent Lifecycle — Create, Configure, Execute

Step 1: Create Agent (UI → API → DB) 
User fills AgentForm
    → POST /api/agents/ { name, role, system_prompt, model, tools, channels, ... }
    → Pydantic validates AgentCreate schema
    → SQLAlchemy inserts into `agents` table
    → Returns AgentResponse with UUID
Step 2: Chat with Agent (UI → API → Runtime → LLM) 
User sends message in ChatPage
    → POST /api/chat/{agent_id} { content: "...", channel: "web" }
    → Saves user Message to DB
    → Calls run_agent() in runtime.py:
        1. Build system prompt + tool instructions + memory context
        2. Assemble message history (last 20 messages)
        3. Call Ollama /api/chat with tools
        4. If tool_calls: execute tools → re-call LLM with results (up to 5 rounds)
        5. If hallucinated tool call detected: intercept → execute → re-call
        6. Store to short-term memory (ChromaDB)
        7. Return { response, tokens_used, tool_calls, memories_stored }
    → Save assistant Message to DB
    → Return response to UI
Step 3: Connect to Telegram 
User adds "telegram" to agent's channels list
    → PUT /api/agents/{id} { channels: ["web", "telegram"] }
    → Agent is now discoverable by the Telegram webhook handler
    → POST /api/telegram/setup-webhook registers with Telegram API

7. LangGraph Runtime Engine — Deep Dive

The runtime engine (runtime.py) implements a single-turn agent execution loop inspired by LangGraph's StateGraph pattern:

┌──────────────┐ │ User Input │ └──────┬───────┘ ▼ ┌──────────────────────┐ │ Build System Prompt │ │ + Tool Instructions │ │ + Memory Context │ └──────────┬───────────┘ ▼ ┌──────────────────────┐ │ Assemble Messages │ │ (history + current) │ └──────────┬───────────┘ ▼ ┌──────────────────────────────┐ │ Call Ollama LLM │ │ POST /api/chat │ │ { messages, tools, options }│ └──────────────┬───────────────┘ ▼ ┌───────────────┐ ┌─NO─┤ Tool Calls? ├─YES─┐ │ └───────────────┘ │ ▼ ▼ ┌────────────────┐ ┌──────────────────────┐ │ Check for fake │ │ Execute Tools via │ │ JSON tool calls│ │ TOOL_REGISTRY │ │ in response │ │ (up to 5 rounds) │ └───────┬────────┘ └──────────┬────────────┘ │ │ ┌────┴────┐ │ ┌─NO─┤ Found? ├─YES──┐ │ │ └─────────┘ │ │ │ ▼ │ │ ┌──────────────────┐ │ │ │ Intercept: │ │ │ │ • Map tool name │ │ │ │ • Parse args │ │ │ │ • Execute tool │ │ │ │ • Re-call LLM │ │ │ └────────┬─────────┘ │ │ │ │ └───────────────────┼─────────────────┘ ▼ ┌────────────────────┐ │ Store to Memory │ │ (STM: user + AI) │ └────────┬───────────┘ ▼ ┌────────────────────┐ │ Return Response │ │ + token count │ │ + tool call log │ └────────────────────┘

7.1 Hallucination Interceptor

Smaller models like llama3.1:8b sometimes "hallucinate" tool calls by writing JSON in their response text instead of using the proper tool-calling mechanism. The interceptor handles this gracefully:

  1. Scans the response text for patterns like {"name": "google_search", ...}
  2. Maps hallucinated tool names to real ones (e.g., google_search → web_search)
  3. Parses arguments including nested JSON and arrays
  4. Executes the real tool and re-calls the LLM with actual results
  5. For array arguments (e.g., multiple search queries), calls the tool once per item

7.2 Tool Calling Loop

When the LLM produces proper tool_calls in its response:

  1. Each tool call is looked up in TOOL_REGISTRY
  2. The tool is invoked with the provided arguments
  3. Special handling for remember_fact: intercepts the __REMEMBER__: prefix and stores the fact in long-term memory
  4. Tool results are appended to the conversation and the LLM is called again
  5. This loops for up to 5 rounds of tool calls to prevent infinite loops

8. Tool Calling Architecture

Tools are registered as plain Python functions decorated with LangChain's @tool decorator, making them compatible with both LangGraph's ToolNode and our direct Ollama integration:

Tool Description Safety Measures
web_search DuckDuckGo search, returns top 5 results with titles, snippets, and URLs Rate-limited by ddgs library
calculator Evaluates math expressions (supports sqrt, sin, cos, log, etc.) Sandboxed eval with __builtins__: {}, only math functions allowed
code_executor Runs Python code in an isolated subprocess 10-second timeout, temporary file, subprocess isolation
file_reader Reads file contents (up to 10KB) Path traversal protection — only allows files within CWD
weather Current weather via wttr.in (no API key needed) 10-second HTTP timeout
summarizer Extractive summary (first, middle, last sentences) Pure text processing, no external calls
current_datetime Returns current UTC date/time Read-only

9. Semantic Memory System

The memory service (memory.py) implements a two-tier architecture using ChromaDB as the vector store and all-MiniLM-L6-v2 for local embeddings:

┌─────────────────┐ │ User Message │ └────────┬────────┘ ▼ ┌──────────────────────┐ │ build_memory_context │ └────────┬─────────────┘ │ ┌───────────┴───────────┐ ▼ ▼ ┌───────────────────┐ ┌───────────────────┐ │ Short-Term Memory│ │ Long-Term Memory │ │ (stm_{agent_id}) │ │ (ltm_{agent_id}) │ ├───────────────────┤ ├───────────────────┤ │ ChromaDB │ │ ChromaDB │ │ Collection │ │ Collection │ │ │ │ │ │ Stores: every │ │ Stores: explicit │ │ user + assistant │ │ facts via │ │ message │ │ remember_fact │ │ │ │ tool or manual │ │ Retrieves: top 5 │ │ │ │ semantically │ │ Retrieves: top 5 │ │ similar past msgs │ │ relevant facts │ └───────────────────┘ └───────────────────┘ │ │ └───────────┬───────────┘ ▼ ┌─────────────────────┐ │ Injected into │ │ System Prompt as: │ │ "[Memory] ..." │ └─────────────────────┘

Key Design Decisions

  • Local embeddings — all-MiniLM-L6-v2 runs locally (~80MB). No API calls, no cost, instant.
  • Cosine similarity — ChromaDB collections use hnsw:space = cosine for semantic matching.
  • Per-agent isolation — Each agent has its own STM and LTM collections (stm_{uuid}, ltm_{uuid}). Agents don't accidentally recall another agent's memories.
  • Automatic storage — Every user message and assistant response is stored in STM after each turn. LTM storage is explicit (via remember_fact tool or manual API).
  • UI Memory Viewer — The AgentsPage includes a modal to browse long-term facts, add/delete facts manually, and perform semantic recall searches.

10. Workflow Engine — Multi-Agent Orchestration

The workflow engine (workflow_engine.py) executes directed graphs of agents using BFS traversal. Each node runs an agent, and edges carry the output text to the next agent.

10.1 Graph Format

{
  "nodes": [
    { "id": "n1", "agent_id": "uuid-of-researcher", "label": "Researcher" },
    { "id": "n2", "agent_id": "uuid-of-editor",     "label": "Editor"     }
  ],
  "edges": [
    { "id": "e1", "source": "n1", "target": "n2", "condition": null }
  ]
}

10.2 Execution Flow

1. Identify START nodes (nodes with no incoming edges) 2. Initialize BFS queue with start nodes + user input 3. For each node in queue: a. If fan-in node (multiple incoming edges): - Wait until ALL source nodes have completed - Merge their outputs with labeled sections b. Load agent from DB c. Execute agent via run_agent() with the input text d. Store output in node_outputs map e. For each outgoing edge: - Evaluate condition (contains, not_contains, max_iterations) - If condition passes, add target to queue with output 4. Collect terminal nodes (nodes with no outgoing edges) as final output 5. Return { status, output, steps }

10.3 Supported Patterns

Pattern Description Example
Sequential A → B → C Researcher → Summarizer → Reviewer
Fan-out A → B, A → C Dispatcher → Sports Reporter, Tech Reporter
Fan-in B → D, C → D All reporters → Editor (merged output)
Conditional A → B (if "APPROVE") Reviewer → Publisher (only if approved)
Feedback Loop A → B → A (max 3) Writer → Critic → Writer (iterate)

10.4 Fan-In Merging

When multiple agents feed into one node (e.g., 3 reporters → 1 editor), the engine:

  1. Builds a reverse adjacency map to detect fan-in nodes
  2. Waits until all source nodes have produced output
  3. Merges outputs with clear labels:
--- Output from Sports Reporter ---
[sports news content]

--- Output from Tech Reporter ---
[tech news content]

--- Output from Politics Reporter ---
[politics news content]

The fan-in node (editor) receives this merged text as its input and produces a single unified response. A deduplication guard (node_id in node_outputs) ensures each node runs exactly once.

10.5 Pre-Built Workflow Templates

Two templates are provided out of the box:

  1. Research & Summarize — A researcher gathers information, then a summarizer condenses it.
  2. Customer Support Escalation — Frontline bot → Specialist (if "ESCALATE") → Manager (if still unresolved). Demonstrates conditional routing.

11.1 Key Design Choices

Challenge Solution
Telegram retries webhook if no quick 200 response Background processing — asyncio.create_task() returns 200 immediately, processes in background
Duplicate messages from retries Message deduplication — tracks message_id in a set, skips if already seen
User doesn't know bot is working Typing indicator — sendChatAction("typing") before processing
Long responses exceed Telegram's 4096-char limit Chunking — splits responses into 4000-char chunks
Want to use workflows, not just single agents Workflow priority — checks for workflow with "telegram" channel first, falls back to agent

11.2 Setup Flow

  1. Create a bot via @BotFather on Telegram → get bot token
  2. Set TELEGRAM_BOT_TOKEN and TELEGRAM_WEBHOOK_URL in .env
  3. Start ngrok tunnel: ngrok http 8000
  4. Set webhook URL to https://<ngrok-url>/api/telegram/webhook
  5. Call POST /api/telegram/setup-webhook to register with Telegram
  6. Assign an agent or workflow to the "telegram" channel via the UI

13. Monitoring & Observability

The platform provides real-time visibility into agent operations:

  • Agent Logs (agent_logs table) — Every significant event is logged:
    • node_started — Workflow node begins execution (with input preview)
    • node_completed — Node finishes (with output preview + token count)
    • agent_not_found — Missing agent error in workflow
  • Message History — All messages (user, assistant, inter-agent) are persisted with:
    • Channel tracking (web, telegram, inter-agent)
    • Token usage per message
    • Cost tracking field (ready for paid model integration)
    • Meta info (Telegram chat_id, sender name, tool calls)
  • Workflow Executions — Each execution records status, input/output data, timestamps, and per-step traces
  • Monitor UI — The MonitorPage fetches logs and messages in real-time with per-agent filtering

15. Security Considerations

Concern Mitigation
Code execution tool Runs in isolated subprocess with 10-second timeout. Temporary file deleted after execution.
File reader path traversal Validates os.path.abspath() starts with CWD. Blocks ../../ attacks.
Calculator eval injection Sandboxed with __builtins__: {}. Only math functions exposed.
Telegram bot token Stored in .env file, never hardcoded. .gitignore excludes .env.
CORS Restricted to localhost:5173 and localhost:3000 only.
SQL injection SQLAlchemy ORM with parameterized queries. No raw SQL.
Input validation Pydantic schemas validate all API inputs (min_length, max_length, types).
Docker images Multi-stage builds with Alpine 3.22 for minimal attack surface.
Memory leak (Telegram dedup) Set evicts after 1000 entries to prevent unbounded growth.

16. Deployment — Docker & Local

16.1 Local Development (Single Setup)

# 1. Clone and enter project
git clone <repo> && cd agents

# 2. Start PostgreSQL and create the database
brew services start postgresql@16
psql postgres -c "CREATE USER agents WITH PASSWORD 'agents_dev';"
psql postgres -c "CREATE DATABASE agents_platform OWNER agents;"
psql postgres -c "GRANT ALL PRIVILEGES ON DATABASE agents_platform TO agents;"
psql agents_platform -c "GRANT ALL ON SCHEMA public TO agents;"

# 3. Start Ollama and pull the model (~4.7 GB download)
ollama serve &
ollama pull llama3.1:8b

# 4. Backend
cd backend
python3 -m venv ../venv && source ../venv/bin/activate
pip install -r requirements.txt
cp ../.env.example .env    # defaults work out of the box
uvicorn app.main:app --reload --port 8000

# 5. Frontend (new terminal)
cd frontend
npm install && npm run dev

# 6. Open http://localhost:5173

16.2 Docker Compose (Full Stack)

# 1. Create backend .env from template
cp .env.example backend/.env

# 2. Build and start all services
docker compose up --build

# 3. Pull the LLM model (first run only, ~4.7 GB)
docker compose exec ollama ollama pull llama3.1:8b

# 4. Open http://localhost:5173 (frontend) or http://localhost:8000/docs (API)

# Stop everything:
docker compose down

# Full reset (wipe DB + model data):
docker compose down -v
Note: The .env file is gitignored. When running inside Docker, the backend reads DATABASE_URL and OLLAMA_BASE_URL from docker-compose.yml environment overrides, so the .env values for those are only used in local development. Telegram tokens must be set in backend/.env if needed.

The docker-compose.yml defines 5 services with health checks and proper dependency ordering:

  • postgres — PostgreSQL 16 Alpine with health check (pg_isready -U agents -d agents_platform)
  • redis — Redis 7 Alpine with health check (redis-cli ping)
  • ollama — Official Ollama image with persistent volume for models
  • backend — Python 3.12-slim with hot-reload via volume mount, depends on postgres + redis + ollama
  • frontend — Uses the build stage of the multi-stage Dockerfile (Node 22 Alpine) with source volume mount and npm run dev for hot-reload. The production Nginx stage is used only for standalone deployment.

17. Trade-offs & Design Decisions

Decision Why Trade-off
Ollama (local LLM) instead of OpenAI API Zero cost, full privacy, no API keys needed, runs offline. Challenge requires "run fully local." Smaller model (8B params) means less capable reasoning and more frequent tool call hallucinations. Mitigated by the hallucination interceptor.
Direct Ollama API calls instead of LangChain ChatOllama More control over tool format, token counting, and error handling. Avoids LangChain version compatibility issues. Slightly more boilerplate for message format conversion. But simpler debugging.
BFS workflow engine instead of async parallel execution Simpler to reason about, deterministic ordering, easier to debug fan-in merging. Agents in fan-out patterns run sequentially, not in parallel. Acceptable for local LLM (single GPU bottleneck anyway).
ChromaDB embedded instead of Pinecone/Weaviate No external service needed. Runs in-process. Perfect for local-first development. Not suitable for production-scale vector search. But meets challenge requirements.
Background task for Telegram instead of message queue Simple asyncio.create_task() avoids needing Celery/RabbitMQ infrastructure. No retry semantics if the background task fails. Mitigated by try/catch with error message to user.
React Flow for workflow builder Purpose-built library for node-based editors. Handles pan, zoom, drag-and-drop, edge rendering. Bundle size is significant (~200KB). Worth it for the functionality provided.
No Alembic migrations — using create_all Faster development iteration. Schema changes applied via manual ALTER TABLE. Not production-ready for schema evolution. Would add Alembic for a production deployment.
Overall Philosophy: Optimize for a working end-to-end demo (40% weight) with clean architecture (30% weight). Every decision prioritizes "does it work locally with zero external dependencies?" while maintaining code quality and clear separation of concerns.
